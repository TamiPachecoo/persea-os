# Future Integration — Google Meet Recordings & Transcripts

This documents where the real Google Meet/Drive/Docs + Supabase integration will connect once this prototype is approved. **Nothing here is implemented.** Per instruction, this pass does not connect Supabase, configure Google Cloud/OAuth, create Edge Functions, or add credentials — everything currently runs on the existing localStorage-backed `MockDB` layer in `app/shared/mock-db.js`, extended in place with the same pattern as every other feature in that file.

**Read this alongside `docs/02-database-schema.md`** (core schema) and `docs/11-agenda-brand-content-schema.md` (the agenda schema this feature extends — `agenda_items`). The recording/transcript bundle below lives on the same table, mirroring how it lives on the `agendaItem` object in the mock layer today.

## ⚠️ Security note — read before connecting anything

Same caveat as `docs/11-agenda-brand-content-schema.md`: today's admin/assistant/client separation is a **UI-only convention** — which page exists, which nav item shows, which `MockDB` getter a screen happens to call. It is **not** a real security boundary. `MockDB.getClientMeetingsWithRecording(clientId)` filters by `relatedStudentId` in JS, in the browser — nothing stops a client-side script from calling it with a different client's id. Real per-client isolation, and real enforcement of "clients never see sync internals," **only exist once Supabase Auth + RLS are actually connected**. This prototype demonstrates the intended experience; it does not yet secure it.

## What's simulated today

- **Recording/transcript URLs** — always mock `https://drive.google.com/...` and `https://docs.google.com/...` strings, some hand-seeded, some generated by the dev `devSimulate*` methods. No video ever plays inside Persea OS — every "Assistir gravação"/"Abrir transcrição" button is a plain external link, by design (also matches the final version: Persea OS should never proxy or embed Google's video player).
- **The meeting → recording lifecycle** (`aguardando → processando → disponível`, plus transcript status) — mutated only by admin-only "Controles da demonstração" buttons, never by anything resembling a real webhook or polling job.
- **"Sincronização com Google"** (`tenant.googleSync` + each meeting's `recording.sync`) — a static object with a fake connected account, fake timestamps, and a fake attempt counter. There is no real OAuth session, no real polling interval, nothing running server-side.
- **Client isolation** — enforced only by which `clientId` the browser's `getActiveClientId()` happens to return (see the client-switcher dev affordance). Real isolation requires Supabase RLS (below).

## Proposed schema extension

```sql
-- Extends agenda_items (docs/11-agenda-brand-content-schema.md) — one
-- recording/transcript bundle per individual_meeting agenda item, not a
-- separate meetings table. 1:1, so a nullable FK works; a join table would
-- be overkill for something that only ever belongs to exactly one meeting.
meeting_recordings (
  id uuid pk,
  tenant_id uuid references tenants(id),
  agenda_item_id uuid references agenda_items(id) unique,

  recording_status text check (recording_status in
    ('aguardando','processando','disponivel','sem_gravacao','erro')),
  transcript_status text check (transcript_status in
    ('aguardando','disponivel','nao_aplicavel','erro')),

  -- Real values: a Google Drive file URL/ID and a Google Docs URL/ID,
  -- fetched via the Meet REST API / Drive API after the conference ends.
  recording_url text,
  recording_drive_file_id text,
  transcript_url text,
  transcript_doc_id text,

  requires_attention boolean default false,
  attention_note text,

  -- Sync bookkeeping — currently mocked in tenant.googleSync +
  -- recording.sync; becomes real once a scheduled job/webhook exists.
  last_checked_at timestamptz,
  next_check_at timestamptz,
  sync_status text check (sync_status in ('aguardando','em_andamento','concluido','erro')),
  sync_attempts int default 0,

  created_at timestamptz,
  updated_at timestamptz
)

-- Tenant-level Google connection (one per tenant/business, not per meeting).
google_connections (
  id uuid pk,
  tenant_id uuid references tenants(id) unique,
  connected_account_email text,
  -- OAuth tokens: never stored in this table directly in plaintext — use
  -- Supabase Vault or an equivalent secret store, referenced by id here.
  oauth_credential_ref text,
  status text check (status in ('ativo','pausado','erro')),
  connected_at timestamptz,
  connected_by uuid references profiles(id)
)
```

RLS follows the same two-policy pattern as the rest of the schema:
- `tenant_admin_all` — Nay/assistant roles can read/write everything for their tenant, including `google_connections` (assistant role should still be denied `oauth_credential_ref` at the column/view level — see below).
- `client_own_rows` — a client can `select` only `meeting_recordings` rows whose `agenda_item_id` belongs to an `agenda_items` row with her own `related_student_id`, and only the columns the client screens actually use (`recording_status`, `transcript_status`, `recording_url`, `transcript_url`) — never `google_connections` or the sync bookkeeping columns.

**Recommendation:** expose a `client_meeting_recordings` view (or Postgres column-level RLS) that excludes `oauth_credential_ref`, `sync_attempts`, `last_checked_at`/`next_check_at`, and `attention_note` from anything the assistant or client roles can query — mirroring exactly what `assistant/recording-detail.js` and `client/encontros.js` already choose not to render in this prototype, but enforced server-side instead of by convention.

## Where the real automation connects

1. **Google OAuth** (Google Cloud Console + Supabase Auth's OAuth provider, or a dedicated service account) — Nay authorizes Persea OS to read her Google Meet/Drive/Docs data once. Token lives behind `google_connections.oauth_credential_ref`, never in client-side code.
2. **A Supabase Edge Function**, triggered either by a Google Meet webhook (if/when available for the relevant Workspace tier) or a scheduled poll (`pg_cron` calling the function every N minutes), that:
   - Looks up `agenda_items` of type `individual_meeting` whose `date` has passed and whose `meeting_recordings.recording_status` isn't yet `disponivel`/`sem_gravacao`.
   - Calls the Google Meet API / Drive API to check for a matching recording file, and the Docs API for the transcript.
   - Updates `meeting_recordings` accordingly, incrementing `sync_attempts` and setting `last_checked_at`/`next_check_at`.
   - Sets `requires_attention = true` with an explanatory `attention_note` after some number of failed attempts (mirrors `devSimulateSyncError` today).
3. **Swap-in point in the code**: every screen in this pass calls `MockDB.getMeetingsOverview()`, `MockDB.getMeetingDetail()`, `MockDB.getClientMeetingsWithRecording()`, etc. — never touches `localStorage` or a URL directly (see the file header of `mock-db.js`). Replacing the mock layer's internals with real Supabase queries (via `@supabase/supabase-js`) means no UI file in `app/admin`, `app/assistant`, or `app/client` should need to change.
4. **Manual fallback stays** — `setRecordingLinks`/`removeRecordingLink`/`markMeetingNoRecording`/`flagMeetingForAttention` become real writes to `meeting_recordings` instead of mock-db mutations; the UI (`openRecordingLinksModal` in `shared/ui.js`) doesn't need to change at all, since it already only calls those `MockDB` methods.
5. **What to delete**: every `devSimulate*`/`devRestore*` method in `mock-db.js`, and the entire "Controles da demonstração" block in `admin/recording-detail.js` — both are explicitly commented as dev-only/removable.

## Non-goals (explicitly out of scope for this pass, and likely out of scope for v1 of the real integration too)

- Playing video inside Persea OS. Every link opens Google's own player in a new tab.
- Automatic transcript summarization/analysis (a separate, already-existing prototype feature — see `transcriptAnalysis` in `mock-db.js` — is unrelated to this recording/transcript *linking* feature and works on manually-uploaded text, not Google Docs).
- Multi-account Google support (one connected account per tenant, matching how Nay's business actually runs today).
